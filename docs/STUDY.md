# 공부할 것 (사전 준비 정리)

> 프로젝트 자체에 대한 설명은 `PROJECT_OVERVIEW.md`를 참고한다. 이 문서는 프로젝트를 만들기 전에 **알아야 할 것 / 필요한 것 / 사용법**을 기능별로 정리한 것이다.

## 한눈에 보기

| # | 주제 | 프로젝트에서 쓰이는 곳 | 필요한 키 | 개발 순서 |
|---|---|---|---|---|
| 1 | 퀴즈 생성용 LLM API | 스토리형 퀴즈의 문제·선택지·해설 생성 | `OPENAI_API_KEY` 또는 `GEMINI_API_KEY` | 4번 (가짜 퀴즈를 AI로 교체) |
| 2 | 음성 AI 대화 | 마이크 녹음 → STT → LLM → TTS | 위의 LLM 키 + STT/TTS 키 (제공자에 따라) | 5번 |
| 3 | 카카오 소셜 로그인 | 회원 가입/로그인 | `KAKAO_CLIENT_ID`, `KAKAO_CLIENT_SECRET`(선택·권장) | 7번 (마지막) |

# 1. 퀴즈 생성용 LLM API

## 1-1. 알아야 할 것

### LLM API란?
백엔드가 OpenAI/Gemini 서버에 **HTTP 요청을 보내고, AI가 생성한 글을 받는 것**이다.

- **REST API**는 통신 방식(HTTP로 GET/POST를 보내고 JSON을 주고받는 규칙)에 대한 이름이고, **LLM API**는 "글을 생성해 주는 서비스"라는 종류에 대한 이름이다. 서로 비교 대상이 아니며, 대부분의 LLM API가 REST 방식이다.
- 일반 REST API와 다른 점은 아래와 같다.

| | 일반 REST API (회원 조회 등) | LLM API |
|---|---|---|
| 응답 | 같은 요청이면 같은 결과 | **같은 요청이어도 매번 달라짐** |
| 결과물 | 정해진 형식의 데이터 | AI가 생성한 글이라 **형식이 깨질 수 있음** |
| 속도 | 수십~수백 ms | **수 초** 걸릴 수 있음 |
| 요금 | 무료이거나 호출 횟수 기준 | **토큰(글자 분량) 기준** |

### 요청/응답 구조
요청에 모델 이름과 메시지 목록을 담아 보내면, 응답으로 생성된 텍스트가 돌아온다. (아래는 개념용 예시이며, 실제 필드 이름은 선택한 제공자의 공식 문서를 따른다.)

```json
{
  "model": "모델이름",
  "messages": [
    { "role": "system", "content": "너는 일본어 퀴즈 출제자야. JSON으로만 답해." },
    { "role": "user",   "content": "핵심 문장: 駅はどこですか ..." }
  ],
  "temperature": 0.7
}
```

### system / user 프롬프트
- `system`: AI의 역할과 규칙을 정하는 고정 지시문 (예: "반드시 JSON으로만 답하라", "정답은 제공된 핵심 문장에 근거해야 한다")
- `user`: 그때그때 바뀌는 재료 (핵심 문장, 스토리 상황, 퀴즈 유형)
- 우리 프로젝트에서는 system에 규칙을, user에 DB에서 꺼낸 문장을 넣는다.

### temperature
답변의 무작위성을 조절하는 값이다. 낮으면 매번 비슷하고 안정적이고, 높으면 다양하지만 형식이 틀어질 위험이 커진다. 퀴즈는 JSON 형식이 깨지면 안 되므로 낮은 값에서 시작해 실험한다.

### 토큰과 비용
AI는 글자 수가 아니라 **토큰** 단위로 요금을 받고, 보낸 프롬프트와 받은 답변 둘 다 계산된다. 프롬프트를 불필요하게 길게 쓰지 않는 것이 중요하고, 퀴즈를 DB에 저장해 재사용하는 방식(2안)이 비용을 줄이는 이유도 여기에 있다.

### 응답이 불확실하다는 것 → 구조화된 출력 + 검증
- **구조화된 출력(Structured Output):** JSON 스키마로 AI의 출력 형식을 강제하는 기능. 제공자별 지원 방식은 공식 문서를 참고한다.
- 그래도 내용이 틀릴 수 있으므로 `PROJECT_OVERVIEW.md`의 **JSON 검증 4단계**를 거친다. LLM 응답은 일반 REST 응답과 달리 받은 그대로 믿고 쓰면 안 된다.

### API 키는 백엔드에서만
키는 곧 결제 수단이다. 프론트 코드에 키가 들어가면 누구나 브라우저 개발자도구에서 꺼내 쓸 수 있고 그 비용이 내게 청구된다. 프론트는 우리 백엔드만 호출하고, 키는 `.env`에서 백엔드로만 읽어 들인다.

## 1-2. 필요한 것

| 항목 | 내용 |
|---|---|
| **제공자 결정** (미정) | OpenAI / Gemini 중 하나. 아래 판단 기준 참고 |
| 계정 + API 키 | 제공자 사이트에서 발급. 사용량 기준 과금이므로 결제 수단 등록이 필요할 수 있음 |
| 사용량/비용 상한 | 콘솔에서 월 한도 설정 (테스트 중 실수로 요금이 커지는 것 방지) |
| `.env` | `OPENAI_API_KEY` 또는 `GEMINI_API_KEY` (쓰는 것만) |
| Spring 쪽 호출 도구 | `RestClient` 등으로 HTTP 호출하거나, 제공자의 공식 Java SDK 사용 |

**제공자 판단 기준** (각 항목은 공식 문서·요금표에서 직접 확인한다)
- 한국어/일본어 퀴즈 품질 (같은 프롬프트로 직접 비교)
- 구조화된 출력(JSON 스키마 강제) 지원 여부
- 요금과 무료 사용량
- 음성(STT/TTS)까지 한 제공자로 통일할 수 있는지 → 통일하면 **키가 1개**로 끝난다.

**주의:** Spring Boot 4는 **Jackson 3**(`tools.jackson` 패키지)을 쓴다. 예전 블로그 예제의 `com.fasterxml.jackson.databind` import와 달라서 JSON 파싱 코드를 옮길 때 import 오류가 날 수 있다.

## 1-3. 사용법 (실습 순서)

1. **API 직접 호출:** 공식 문서의 예제 요청을 curl/Postman으로 그대로 보내 본다. 요청과 응답 JSON 구조를 눈으로 확인한다.
2. **프롬프트 작성 연습:** 대상 문장, 상황, 수준, 출력 형식, 예시 1~2개를 넣어 본다. **같은 프롬프트를 10번 돌려서** 결과가 얼마나 흔들리는지 비교한다.
3. **출력 형식 강제:** 구조화된 출력으로 `PROJECT_OVERVIEW.md` 5장의 퀴즈 JSON 형식이 나오게 만든다.
4. **Spring으로 감싸기:** 퀴즈 생성 서비스를 만든다. `호출 → 파싱 → 4단계 검증 → 실패 시 재시도/대체`
5. **운영 대비:** 타임아웃, 호출 실패 시 대체(fallback) 퀴즈, 사용량 제한, 비용 상한을 넣는다.
6. **화면 연결:** 프론트가 우리 백엔드의 퀴즈 API만 호출하도록 연결한다.

**확인 체크리스트**
- [ ] 제공자를 정했다
- [ ] curl로 응답을 받아 봤다
- [ ] 같은 프롬프트를 10번 돌려 형식이 깨지는 비율을 확인했다
- [ ] 키가 코드가 아니라 `.env`에만 있다
- [ ] 월 비용 상한을 설정했다

# 2. 음성 AI 대화

## 2-1. 알아야 할 것

### 전체 흐름
```
[프론트] 마이크 녹음 → FormData로 업로드
   ↓
[백엔드] STT(음성→텍스트) → LLM(답변 생성) → TTS(텍스트→음성)
   ↓
[프론트] 음성 재생 + 텍스트 표시
```
3단계가 **직렬**이라 응답에 수 초가 걸린다. 로딩 UI("듣는 중 / 생각 중 / 말하는 중")를 미리 설계한다.

### 브라우저 녹음
- `getUserMedia`로 마이크 권한을 받고, `MediaRecorder`로 녹음한다.
- **HTTPS가 필요**하다 (localhost는 예외). 배포 시 HTTPS가 없으면 마이크를 쓸 수 없다.
- 녹음 포맷이 브라우저마다 다르다 (Chrome은 webm, Safari는 mp4인 경우가 많음). STT가 받을 수 있는 포맷인지 확인한다.

### 업로드
- 녹음 파일을 `FormData`에 담아 전송하면 백엔드는 **multipart** 요청으로 받는다 (Spring의 `MultipartFile`).
- 파일 크기 제한 설정(`spring.servlet.multipart.max-file-size` 등)을 확인한다. 기본 제한에 걸려 업로드가 실패할 수 있다.

### STT (음성 → 텍스트)
- 언어를 지정한다 (한국어/일본어/영어). 언어를 지정하지 않으면 인식 정확도가 떨어질 수 있다.
- 지원하는 파일 형식과 파일 크기 제한은 제공자 문서에서 확인한다.

### LLM 대화
- LLM은 **이전 대화를 기억하지 않는다.** 대화를 이어가려면 이전 발화를 매 요청마다 함께 보내야 한다. (대화 기록을 DB에 저장하지 않는다면, 프론트가 기록을 들고 있다가 요청에 실어 보낸다.)
- system 프롬프트로 역할극을 정한다 (예: "일본어 초급자를 위한 카페 점원 역할, 짧고 쉬운 문장으로 답하라").
- 답변을 짧게 하도록 지시하면 TTS 길이, 지연시간, 비용이 함께 줄어든다.

### TTS (텍스트 → 음성)
- 텍스트를 보내면 음성 파일이 돌아온다. 언어와 목소리를 고를 수 있다.
- 브라우저는 **사용자 조작 없이 자동 재생을 막는 경우**가 있다. 재생은 사용자가 버튼을 누른 이후에 시작되도록 설계한다.

## 2-2. 필요한 것

| 항목 | 내용 |
|---|---|
| STT 제공자 | 예: OpenAI(Whisper). 키 필요 |
| LLM 제공자 | 1번에서 정한 것 그대로 (같은 키) |
| TTS 제공자 | ElevenLabs 또는 OpenAI. ElevenLabs는 별도 키(`ELEVENLABS_API_KEY`) 필요 |
| 프론트 스택 (미정) | 녹음/재생 UI를 만들 프론트 프레임워크 결정 |
| Spring 설정 | multipart 업로드 크기 제한 |
| 테스트 환경 | 개발은 localhost, 배포는 HTTPS |

**키를 줄이는 방법:** OpenAI로 통일하면 STT + LLM + TTS를 키 하나로 처리할 수 있다. Gemini나 ElevenLabs를 섞으면 키가 그만큼 늘어난다.

## 2-3. 사용법 (실습 순서)

단계마다 **단독으로 성공한 뒤** 다음을 붙인다.

1. **TTS 단독:** 텍스트를 보내 음성 파일을 받고, 저장해서 재생해 본다.
2. **STT 단독:** 샘플 녹음 파일을 보내 텍스트가 나오는지 확인한다. 한국어/일본어를 각각 시험한다.
3. **브라우저 녹음:** 프론트에서 `MediaRecorder`로 녹음하고 바로 재생해 본다. Chrome과 Safari 포맷 차이를 확인한다.
4. **업로드:** 녹음 파일을 `FormData`로 백엔드에 보내고, 서버에 파일이 도착했는지 확인한다.
5. **STT 연결:** 업로드된 파일 → 텍스트 응답만 돌려준다.
6. **LLM 연결:** 텍스트 + 이전 대화 → AI 답변 텍스트를 돌려준다.
7. **TTS 연결:** AI 답변 → 음성으로 변환해 응답 (음성 URL + 텍스트).
8. **화면 마무리:** 로딩 상태 표시, 재생 버튼, 실패 시 안내를 넣는다.

**확인 체크리스트**
- [ ] STT/TTS 제공자를 정했다
- [ ] localhost에서 마이크 권한과 녹음이 된다
- [ ] Chrome, Safari 둘 다에서 녹음 파일이 STT에 통과한다
- [ ] 업로드 크기 제한에 걸리지 않는다
- [ ] 3단계 전체 응답 시간을 측정해 봤다
- [ ] 자동 재생이 막히지 않도록 재생을 버튼으로 시작한다

# 3. 카카오 소셜 로그인

> 개발 우선순위는 낮다. 개발 중에는 DB에 테스트 유저 1명을 넣고 `user_id = 1`로 고정해서 쓰다가, 마지막에 로그인을 붙인다.

## 3-1. 알아야 할 것

### OAuth2 인가 코드 흐름
카카오 로그인은 우리가 비밀번호를 받지 않고, **카카오가 사용자를 인증해 준 결과를 받는 방식**이다.

```
① 사용자가 "카카오로 로그인" 클릭
② 카카오 로그인·동의 화면 표시 → 사용자가 로그인하고 동의
③ 카카오가 우리 서버의 Redirect URI로 인가 코드(code)를 전달
④ 우리 서버가 인가 코드로 카카오에 액세스 토큰을 요청
⑤ 액세스 토큰으로 사용자 정보 조회 (회원번호, 닉네임 등)
⑥ 우리 DB에서 가입 여부 확인 → 없으면 가입, 있으면 로그인
⑦ 로그인 상태를 유지 (세션 또는 JWT)
```

### 용어

| 용어 | 뜻 |
|---|---|
| 인가 서버 | 카카오 |
| 클라이언트 | 우리 서비스 (Kakao Developers에 등록한 앱) |
| 인가 코드 | 로그인 성공 후 카카오가 Redirect URI로 넘겨주는 1회용 코드 |
| 액세스 토큰 | 인가 코드를 교환해 얻는, 사용자 정보를 조회할 수 있는 열쇠 |
| Redirect URI | 로그인 후 카카오가 돌아올 우리 서버 주소. **콘솔에 등록한 주소와 정확히 일치**해야 함 |
| 동의항목 | 사용자에게 받는 정보의 종류 (닉네임, 프로필 사진, 이메일 등) |

### Spring이 대신 해 주는 부분
- 프로젝트에는 `spring-boot-starter-security-oauth2-client`가 이미 들어 있다. 위 ①~⑤의 통신은 이 라이브러리가 처리하므로, 우리가 직접 만드는 부분은 **⑥ 회원 가입/로그인 처리와 ⑦ 로그인 상태 유지**다.
- 카카오는 Spring이 기본 제공하는 provider(Google, GitHub 등)가 아니므로, **카카오의 주소들을 설정 파일에 직접 적어야** 한다.

### 사용자 정보 응답 구조
카카오의 사용자 정보는 중첩 JSON이다. 대략 이런 모양이다 (정확한 구조는 공식 문서 확인).
```
id                        ← 카카오 회원번호 (→ USERS.kakao_id)
kakao_account
  ├─ profile.nickname      ← 닉네임 (→ USERS.nickname)
  └─ email                 ← 이메일 (동의 안 하면 없음 → USERS.email nullable)
```

### 로그인 후 상태 유지: 세션 vs JWT (미정)
- **세션:** 서버가 로그인 상태를 기억하고 쿠키로 식별. 구현이 단순하다.
- **JWT:** 서버가 서명된 토큰을 발급하고 프론트가 매 요청에 첨부. 프론트/백엔드가 분리돼 있을 때 흔히 쓰지만 `JWT_SECRET` 관리 등 구현할 것이 늘어난다.
- 프론트 스택과 배포 구조가 정해지면 결정한다.

### 개발 중 주의: Spring Security가 모든 요청을 막는다
`spring-boot-starter-security`가 들어 있으면 **설정을 하지 않아도 모든 URL이 로그인 요구**로 막힌다. 그래서 다른 기능을 개발하는 동안 Postman으로 API를 호출하면 401/로그인 페이지 리다이렉트가 나오고, POST 요청은 CSRF 때문에 403이 날 수 있다. 개발 중에는 `SecurityFilterChain`에서 API 경로를 임시로 열어 둔다.

## 3-2. 필요한 것

## 3-3. 사용법

### `application.yaml` 설정 (개념용 스케치)
```yaml
spring:
  security:
    oauth2:
      client:
        registration:
          kakao:
            client-id: ${KAKAO_CLIENT_ID}
            client-secret: ${KAKAO_CLIENT_SECRET}
            client-authentication-method: client_secret_post
            authorization-grant-type: authorization_code
            redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}"
            scope: profile_nickname
            client-name: Kakao
        provider:
          kakao:
            authorization-uri: https://kauth.kakao.com/oauth/authorize
            token-uri: https://kauth.kakao.com/oauth/token
            user-info-uri: https://kapi.kakao.com/v2/user/me
            user-name-attribute: id
```
- 로그인 시작 주소는 `/oauth2/authorization/kakao`, 카카오가 돌아오는 주소는 `/login/oauth2/code/kakao`이다 (Spring 기본값).
- Client Secret을 사용하지 않기로 했다면 `client-secret` 줄은 뺀다.
- 필요한 동의항목(scope)은 카카오 콘솔의 동의항목 설정과 맞춘다.

### 우리가 만드는 부분 (구조만)
```
SecurityConfig
  └─ SecurityFilterChain 에 oauth2Login 설정
       └─ 로그인 성공 시 → 커스텀 OAuth2UserService 호출
            1) 카카오 응답에서 id, 닉네임, 이메일 꺼내기
            2) USERS에서 kakao_id로 조회
            3) 없으면 새로 저장(가입), 있으면 그대로(로그인)
       └─ 로그인 성공 후 이동할 주소 (프론트 화면) 지정
```

### 실습 순서
1. **카카오 앱 준비:** 앱 생성 → REST API 키 확인 → 카카오 로그인 ON → Redirect URI 등록 → 동의항목 설정 → (선택) Client Secret 설정
2. **흐름 체험:** 카카오 개발자 콘솔의 REST API 테스트 도구나 공식 튜토리얼로, 인가 코드 → 토큰 → 사용자 정보 조회 과정을 한 번 눈으로 확인한다.
3. **Spring 설정으로 로그인 화면까지:** 위 yaml을 넣고 `/oauth2/authorization/kakao`에 접속해 카카오 로그인 화면이 뜨는지 확인한다.
4. **사용자 정보 확인:** 로그인 후 받은 사용자 정보(id, 닉네임)를 로그로 찍어 본다.
5. **DB 연동:** `kakao_id`로 조회 → 없으면 가입하는 로직을 붙인다.
6. **로그인 상태 유지 + 프론트 연동:** 세션 또는 JWT 방식을 정하고, 로그인 성공 후 프론트로 이동하도록 연결한다. 프론트와 백엔드 주소가 다르면 CORS/쿠키 설정도 확인한다.
7. **고정값 교체:** 개발용으로 쓰던 `user_id = 1`을 로그인한 사용자로 바꾼다.

**확인 체크리스트**
- [ ] Kakao Developers에서 로그인 ON, Redirect URI 등록을 했다
- [ ] `.env`에 `KAKAO_CLIENT_ID`(와 Client Secret 사용 시 `KAKAO_CLIENT_SECRET`)가 있다
- [ ] 로그인 화면이 뜬다
- [ ] 사용자 정보가 로그에 찍힌다
- [ ] 같은 카카오 계정으로 다시 로그인해도 USERS에 중복 가입되지 않는다
- [ ] 이메일 동의를 안 해도 로그인이 된다
- [ ] 배포 시 Redirect URI와 사이트 도메인을 실제 주소로 추가 등록한다 (HTTPS)
